# 简历亮点三：三态熔断器 + TTFB 探测 + 多模型自动降级

## 一、简历原文

> 引入三态熔断器与流式首包(TTFB)探测，实现多模型节点在**首包前**的自动降级与安全切换，保障核心问答链的高可用性

## 二、业务背景

系统接入了多个大模型供应商，普通同步调用失败时，可以在调用点直接 catch 异常，然后切换到下一个候选模型；但流式调用不是这样。

`client.streamChat()` 调用后会立刻返回一个取消句柄，真正的数据和错误是在异步线程里通过回调持续推回来的：

- `onContent()`：收到正文 token
- `onThinking()`：收到思考内容
- `onComplete()`：流正常结束
- `onError()`：流过程中报错

这会带来两个核心问题：

1. **返回时无法立刻判断当前候选是否真的成功**
   - 句柄已经返回了，但首个 token 可能还没到
   - 路由层这时不知道应该返回当前流，还是切换到下一个候选

2. **失败候选一旦输出过内容，就无法回滚**
   - 如果候选 A 先输出了几个 token，前端已经开始渲染
   - 后面 A 再报错并切到候选 B
   - 用户看到的就会是“前一个模型的残片 + 后一个模型的完整答案”

所以这个亮点真正解决的不是普通的“多模型重试”，而是：

> **如何在流式调用的异步模型下，既尽早判断候选是否可用，又保证失败候选的半截内容绝不泄漏给用户。**

## 三、整体流程

### 3.1 总体思路

整套方案的核心不是把供应商的流式输出直接透传给前端，而是在真实 callback 前面加一层 `ProbeStreamBridge`。

它把一次流式候选尝试拆成两个阶段：

- **probe（探测）**：先接住供应商回调，缓冲事件，不立刻下发给真实 callback
- **commit（提交）**：只有确认当前候选已经真正开始响应，才把缓冲内容按顺序回放，并切换为实时透传

一句话概括就是：

> **先探测，再提交；成功才放行，失败就丢弃。**

### 3.2 流式路由总流程

```text
用户发起流式请求
  │
  ▼
RoutingLLMService.streamChat(request, callback)
  │
  ├── selector.selectChatCandidates(...) 选择候选模型
  │
  ├── for 循环遍历候选
  │     │
  │     ├── healthStore.allowCall(target.id())
  │     ├── 创建 ProbeStreamBridge bridge
  │     ├── handle = client.streamChat(request, bridge, target)
  │     ├── result = firstPacketProbe.awaitFirstPacket(bridge, 60s)
  │     │
  │     ├── SUCCESS
  │     │     ├── ProbeStreamBridge.awaitFirstPacket() 内部自动 commit
  │     │     ├── healthStore.markSuccess(target.id())
  │     │     └── return handle
  │     │
  │     └── ERROR / TIMEOUT / NO_CONTENT
  │           ├── healthStore.markFailure(target.id())
  │           ├── handle.cancel()
  │           └── continue 下一个候选
  │
  └── 所有候选都失败
        ├── callback.onError(...)
        └── throw RemoteException
```

### 3.3 与同步 `chat()` 的本质区别

| 维度 | `chat()`（同步） | `streamChat()`（流式） |
|------|------------------|------------------------|
| 成败判断 | 返回值 / 异常 | 首包探测结果 |
| 故障检测 | try-catch 即可 | 必须等待异步回调首个信号 |
| 路由方式 | `executeWithFallback()` | 自己实现候选遍历与切换 |
| 输出策略 | 直接返回完整结果 | 先缓冲，成功后再放行 |
| 失败代价 | 失败即切换 | 失败前不能让半截输出泄漏 |

## 四、完整处理链路

### 4.1 单个候选的完整处理链路

```text
开始尝试某个候选模型
  │
  ├── 1. healthStore.allowCall(target.id())
  │      判断这个模型当前是否允许被调用
  │      CLOSED / HALF_OPEN 可继续，OPEN 直接跳过
  │
  ├── 2. 创建 ProbeStreamBridge
  │      作为真实 callback 前面的桥接层
  │
  ├── 3. 调用 client.streamChat(request, bridge, target)
  │      供应商开始异步推送流式事件
  │      此时返回 handle，但还不能直接认定成功
  │
  ├── 4. 所有事件先进入 bridge
  │      onContent / onThinking / onComplete / onError
  │      先不透传给真实 callback
  │
  ├── 5. bridge 内部同时做两件事
  │      5.1 缓冲事件
  │          把事件封装成 Runnable，先存入 buffer
  │      5.2 写入首包探测结果
  │          第一个到达的信号写入 CompletableFuture<ProbeResult>
  │
  ├── 6. 路由线程同步等待 bridge.awaitFirstPacket(...)
  │      最多等待 60 秒
  │      当前通过 LlmFirstPacketProbe 独立 bean 调用，方便 @RagTraceNode 采集首包等待耗时
  │      得到四种结果之一：
  │      - SUCCESS
  │      - ERROR
  │      - TIMEOUT
  │      - NO_CONTENT
  │
  ├── 7. 如果结果是 SUCCESS
  │      ├── ProbeStreamBridge.awaitFirstPacket() 内部自动触发 commit()
  │      ├── 把之前缓冲的事件按顺序回放给真实 callback
  │      ├── 后续新事件不再缓冲，直接实时透传
  │      ├── healthStore.markSuccess(target.id())
  │      └── 返回当前 handle，流式输出正式继续
  │
  ├── 8. 如果结果是 ERROR / TIMEOUT / NO_CONTENT
  │      ├── 不 commit，缓冲事件整批丢弃
  │      ├── healthStore.markFailure(target.id())
  │      ├── handle.cancel()
  │      └── 继续尝试下一个候选模型
  │
  └── 9. 如果所有候选都失败
         ├── callback.onError(...)
         └── throw RemoteException
```

### 4.2 ProbeStreamBridge 内部处理链路

```text
供应商异步回调进入 ProbeStreamBridge
  │
  ├── onContent(content)
  │     ├── probe.complete(SUCCESS)
  │     └── bufferOrDispatch(() -> downstream.onContent(content))
  │
  ├── onThinking(content)
  │     ├── probe.complete(SUCCESS)
  │     └── bufferOrDispatch(() -> downstream.onThinking(content))
  │
  ├── onComplete()
  │     ├── probe.complete(NO_CONTENT)
  │     └── bufferOrDispatch(downstream::onComplete)
  │
  └── onError(t)
        ├── probe.complete(ERROR)
        └── bufferOrDispatch(() -> downstream.onError(t))
```

这里最关键的是两点：

1. **只认第一个探测结果**
   - `CompletableFuture.complete()` 只有第一次生效
   - 谁先到，谁就是这次候选的首包判定结果

2. **探测成功前，所有事件都只是缓冲，不会真正下发**
   - 这样失败候选即使收到过内容，也不会泄漏给用户

### 4.3 `bufferOrDispatch` 和 `commit` 的并发关系

这是整个桥接器最关键的并发点：

- `bufferOrDispatch(...)`：运行在异步流线程
- `commit()`：运行在路由线程

两者会并发访问：

- `committed`
- `buffer`

所以必须使用同一把锁互斥。

如果不加锁，会有三个直接问题：

1. **事件丢失**
   - 流线程刚判断 `committed=false`
   - 还没把事件放进 `buffer`
   - 路由线程先执行完 `commit()`
   - 后面这个事件既没被回放，也不会再直通，直接丢失

2. **并发修改异常**
   - `commit()` 正在遍历 `buffer`
   - 流线程同时执行 `buffer.add(...)`
   - 可能触发 `ConcurrentModificationException`

3. **事件乱序**
   - 缓冲入队和提交回放如果不互斥
   - 前端收到的流式顺序就可能被打乱

所以正确做法是：

> **要么事件先安全入队，再被 commit 顺序回放；要么 commit 已经完成，后续事件直接走实时透传。**

### 4.4 为什么要有 `LlmFirstPacketProbe`

当前代码没有让 `RoutingLLMService` 直接调用 `bridge.awaitFirstPacket()`，而是通过独立的 `LlmFirstPacketProbe` Bean 包一层：

```java
@RagTraceNode(name = "llm-first-packet", type = "LLM_TTFT")
public ProbeStreamBridge.ProbeResult awaitFirstPacket(ProbeStreamBridge bridge,
                                                      long timeout,
                                                      TimeUnit unit) throws InterruptedException {
    return bridge.awaitFirstPacket(timeout, unit);
}
```

这么做不是为了多一层抽象，而是为了让首包等待进入 RAG trace。Spring AOP 不会拦截同一个类里的 self-call，如果把 `@RagTraceNode` 直接标在 `RoutingLLMService` 内部私有方法上，首包探测耗时无法稳定被切面采集。拆成独立 Bean 后，路由层调用的是 Spring 代理对象，`LLM_TTFT` 节点才能记录下来。

## 五、三态熔断器在这条链路里的作用

虽然这个亮点的重点是首包探测，但三态熔断器仍然是整个链路里不可缺少的上游过滤器。

它和首包探测分别解决不同层次的问题：

- `ModelHealthStore`：判断这个模型最近整体健不健康，是否应该先跳过
- `ProbeStreamBridge`：判断这一次请求里，这个模型是否已经真正开始响应

所以两者的关系是：

- **熔断器：粗筛**
- **首包探测：细筛**

三态状态流转如下：

```text
CLOSED（正常）
  ├── 连续失败达到阈值 → OPEN
  │
  ▼
OPEN（熔断）
  ├── 冷却期内直接拒绝调用
  └── 冷却结束后，下一次 allowCall → HALF_OPEN
       │
       ├── 探测成功 → CLOSED
       └── 探测失败 → OPEN
```

这里 `HALF_OPEN` 的关键不是周期性探测，而是：

> **只放一次恢复性试探流量。**

## 六、面试题（架构设计版）

> 这一组题只讨论架构设计、设计取舍和系统边界，不展开到具体方法实现细节。

### Q1：你这个流式高可用方案整体是怎么设计的？为什么这里需要额外做首包探测？

**标准回答：**

这套方案可以按四步来理解：

1. 先从配置里选出一组候选模型
2. 在真正发请求前，先做一次模型健康检查，过滤近期明显不健康的候选
3. 发起流式请求时，不把真实 callback 直接交给供应商，而是在前面加一层 `ProbeStreamBridge`
4. 路由线程通过 `LlmFirstPacketProbe` 等待首包探测结果，并采集 `LLM_TTFT` trace：
   - 如果探测成功，就自动 `commit`，把前面缓冲的事件刷给真实 callback，后续内容开始直通
   - 如果探测失败、超时或无内容完成，就取消当前候选，切到下一个模型

这里之所以需要额外做首包探测，是因为流式调用和同步调用的成败判定时机不一样。

同步调用里，方法返回时结果已经确定了：

- 成功就返回结果
- 失败就抛异常

但流式调用不是这样。`streamChat()` 返回得很快，返回的是一个取消句柄，不是最终结果。真正的数据和错误是后面异步线程通过回调慢慢推回来的。也就是说，**调用返回的那一刻，路由层其实还不知道当前候选是否真的可用。**

所以必须额外补一个“同步决策点”，把异步世界里的第一个关键信号重新拉回路由层来判断。这里选的就是“首包是否到达”。

**具体示例：**

假设候选顺序是：

- 模型 A：本地 `Ollama`
- 模型 B：云端 `qwen-plus`

请求进来后，路由层先尝试 A。A 的 `streamChat()` 很快返回了句柄，但这不代表它真的能正常出内容。此时系统不会直接把 A 的输出透传给前端，而是先通过桥接层接住事件并等待首包。

如果 A 在首 token 前因为显存溢出崩溃：

- 前端这时还没收到任何内容
- 路由层会判定 A 本次失败
- 取消 A
- 切到 B

最后前端只会看到 B 的正常回答，而不会看到 A 的半截残片。

### Q2：为什么这里既要做模型健康检查，又要做首包探测？这两层分别解决什么问题？

**标准回答：**

这两层看起来都在判断“模型能不能用”，但判断的不是同一个维度：

| 层次 | 解决的问题 |
|------|------------|
| 模型健康检查 | 这个模型**最近一段时间**整体健不健康，值不值得先尝试 |
| 首包探测 | 这个模型在**当前这一次请求**里，是否已经真正开始响应 |

也就是说：

- 健康检查看的是**历史健康度**
- 首包探测看的是**当次实时状态**

顺序上也是这样的：

1. 先做健康检查
2. 如果健康检查放行，才真正发起流式请求
3. 请求发出去后，再做首包探测

如果只有健康检查，没有首包探测，会漏掉一种情况：

> 模型历史上一直很健康，但这一次请求恰好在首包前崩溃。

如果只有首包探测，没有健康检查，也不行。因为那些已经明显不健康的模型，每次请求还得真的去试一次、等一次、超时一次，系统会持续浪费时间。

所以这两层是互补关系，不是重复设计。

**具体示例：**

假设本地模型 A 过去一天都很稳定，所以健康状态一直是正常的。现在一条特别长的请求进来，A 在首 token 前 OOM 了。

这时：

- 健康检查会先放行，因为它看的是历史
- 首包探测会在当前请求里发现：这次根本没真正出内容
- 系统马上取消 A，切到下一个候选

反过来，如果模型 B 最近连续多次失败，健康检查就应该先把它挡掉，避免每次都再花时间去探测它。

### Q3：为什么故障转移的边界要卡在首包前，而不是整条流全过程都自动切换？

**标准回答：**

因为“首包前”和“首包后”是两个完全不同的系统状态。

首包前：

- 事件还只是缓存在桥接层里
- 真实 callback 还没有收到任何内容
- 前端还没有开始渲染

所以这个阶段切换是安全的。失败候选的缓冲内容可以整批丢弃，用户不会感知到。

首包后就不一样了。一旦已经 `commit`：

- 内容已经开始下发给真实 callback
- 前端已经开始看到这一个模型的输出

如果这时候再切到另一个模型，前端就会看到：

- 前一个模型的半截内容
- 后一个模型重新生成的完整内容

结果会出现重复、断裂甚至语义冲突。

所以这条链路必须明确一个边界：

> **commit 之前可以切，commit 之后不再切。**

这不是实现习惯，而是用户可见一致性的要求。

**具体示例：**

假设模型 A 先输出了：

- `AirPods`
- ` Pro`

此时前端已经开始渲染“AirPods Pro”。

如果 A 后面再报错，而系统又切到模型 B，B 很可能会重新从头回答：

- `AirPods Pro 2 的保修期是……`

这样前端看到的就会是：

- A 的残片
- B 的完整答案

内容会重复，而且很难让用户理解到底哪个才是最终结果。

**补充说明：**

首包正常以后，后续中断当然仍然可能发生，比如：

- 网络中断
- 本地模型生成到一半崩溃
- 运行过程中的偶发异常

这种情况系统不会再自动切换，而是把错误直接暴露给上层。因为此时再切换，代价已经不是“多等一下”，而是会破坏前端已经看到的内容一致性。

### Q4：如果一个模型历史上一直健康，但这一次请求恰好在首包前崩溃，系统怎么兜底？为什么健康检查本身不够？

**标准回答：**

这类场景正是首包探测存在的意义。

健康检查只能回答：

> 这个模型最近是不是整体健康？

但它回答不了：

> 这一次请求，它此刻是不是一定能正常出内容？

所以当一个模型历史上一直健康时，健康检查通常会先放行；真正的兜底发生在首包探测阶段。

系统会这样处理：

1. 健康检查先放行当前候选
2. 流式请求发出去，但内容先缓冲，不立刻透传
3. 路由线程等待首包结果
4. 如果在首包前收到错误、超时或者无内容完成，就判定当前候选失败
5. 取消当前流，切下一个候选
6. 同时把这次失败记入模型健康状态，供后续熔断判断使用

也就是说，健康检查负责“要不要试”，首包探测负责“这次试得成不成”。

**具体示例：**

假设本地 `Ollama` 模型过去 100 次调用都正常，所以健康检查会认为它可用。  
但这次请求特别长，模型在生成第一个 token 前就因为 OOM 崩掉了。

如果只有健康检查，没有首包探测：

- 这次请求就会直接失败
- 用户会感知到一次明显中断

如果有首包探测：

- 系统会发现这次请求根本没真正进入可放行状态
- 当前候选被取消
- 立即切到下一个候选
- 前端仍然不会看到失败模型的半截内容

### Q5：这套方案适用于什么场景？你怎么判断它值得做，还是复杂度过高？

**标准回答：**

这套方案不是所有项目都必须上。它更适合下面这类场景：

- 有多模型候选，需要在核心问答链路上做高可用
- 存在流式输出，不是普通同步请求
- 使用本地部署模型较多，比如 `Ollama`、`vLLM`
- 业务上不能接受失败候选把半截内容泄漏给前端

它特别有价值的，是这种故障模式：

> HTTP 连接已经建立，请求也已经被接受，但模型在首包前崩溃。

这类问题在本地部署模型承压场景更常见，比如：

- 显存溢出
- 推理进程重启
- 节点短暂失活

如果主要接的是成熟云厂商 API，这套机制的投入产出比通常会下降。因为云厂商后面往往已经有负载均衡、节点隔离和平台级容错，请求方更常见的是：

- 要么快速返回 HTTP 错误
- 要么正常出流

这时候再引入首包同步等待、桥接缓冲和候选切换，未必一定划算。

所以判断这套方案值不值得做，不是看“它技不技术”，而是看：

1. 你的故障模式是不是集中在流式异步场景
2. 失败候选泄漏半截内容这件事，对用户体验是不是高风险
3. 你是不是确实有多候选模型可切
4. 这条链路是不是核心链路，值得为高可用投入额外复杂度

**具体示例：**

如果系统主要依赖本地 `Ollama` 和自建 `vLLM`，并且聊天回答直接面向用户，这套方案就很值得做。因为一旦某个本地节点在首包前崩掉，没有这层探测和缓冲，用户很容易直接看到失败或残片。

但如果系统主要接的是成熟云 API，而且供应商本身已经做了很强的平台级高可用，这套复杂度就要重新评估，不一定值得原样引入。
