# 简历亮点二：知识库定时同步引擎（Schedule 模块）

## 一、简历原文

> 设计知识库**定时同步引擎**，基于 **数据库租约锁**与**自适应心跳续期**实现多节点安全调度，通过**分阶段错误恢复**保障异常场景下零资源泄漏

## 二、业务背景

用户为知识库配置了远程 URL 来源的文档（如飞书文档、在线 API 文件等），并设置了 cron 定时表达式。系统需要定期从远程地址拉取最新版本，重新分块、向量化，更新知识库内容，确保知识始终是最新的。

## 三、整体流程

### 3.1 两个定时任务

| 任务 | 触发频率 | 作用 |
|------|---------|------|
| 主扫描 `scan()` | 每 10 秒 | 查找到期需执行的调度任务，抢锁后提交线程池异步处理 |
| 看门狗 `recoverStuckRunningDocuments()` | 每 60 秒，启动后延迟 30 秒第一次执行 | 批量重置卡在 RUNNING 状态超过配置阈值的文档为 FAILED（`runningTimeoutMinutes` 默认 30 分钟，最小按 10 分钟兜底） |

### 3.2 单条记录的完整处理链路

```
scan() 查询候选记录
  │  条件：enabled=1 AND (nextRunTime<=now) AND (lock_until IS NULL OR lock_until<now)
  │  排序：nextRunTime ASC，最多 20 条
  ▼
lockManager.tryAcquire() —— 抢分布式锁
  │  SQL: UPDATE ... SET lock_owner=token, lock_until=now+900s
  │       WHERE id=? AND (lock_until IS NULL OR lock_until<now)
  │  原子操作，只有一个实例成功（affected rows=1）
  ▼
提交至线程池异步执行 → processor.process(lease)
  │
  ├── 1. 启动心跳线程（ScheduleLockHeartbeat）
  │     间隔 = max(5, min(TTL/3, 60)) 秒；TTL=900s 时，间隔 = max(5, min(300, 60)) = 60 秒
  │     每次续约：UPDATE ... SET lock_until=now+900s WHERE lock_owner=token
  │     条件更新 0 行表示锁已被别人拿走，立即标记丢锁
  │     数据库临时异常则继续重试，只有 当前时间-lastConfirmedAt >= TTL 才标记丢失
  │
  ├── 2. 加载文档，校验存在性、是否启用
  │
  ├── 3. 解析 cron，计算下次执行时间
  │
  ├── 4. 插入执行记录（exec 表，状态 RUNNING）
  │
  ├── 5. fetchIfChanged() —— ETag 条件请求
  │     文件未变 → 标记 SKIPPED，return
  │     文件已变 → 下载到临时文件
  │
  ├── 6. tryMarkRunning(docId) —— CAS 抢文档运行权
  │     SQL: UPDATE ... SET status=RUNNING WHERE status!=RUNNING
  │     失败 → 其他线程正在处理，标记 SKIPPED，return
  │     成功 → phase = DOC_OCCUPIED
  │
  ├── 7. 上传新文件到对象存储
  │
  ├── 8. phase = CHUNK_STARTED
  │     调用 chunkDocument() → 解析、分块、向量化、写入向量库（当前默认 PGVector，代码保留 Milvus 可切换实现）
  │
  ├── 9. 检查分块结果
  │     失败 → 标记 FAILED，return
  │     成功 → phase = CHUNK_COMPLETED
  │
  ├── 10. applyRefreshedFileMetadata() —— 切换文件元数据
  │      更新 docName、fileUrl、fileType、fileSize
  │      phase = FILE_SWITCHED
  │
  ├── 11. 写回调度状态（带 lock_owner 条件，乐观并发）
  │      返回 0 行 → 锁已丢失 → leaseLost = true
  │
  └── finally 块 —— 分阶段清理
        │
        ├── heartbeat.close() —— 停止心跳
        │
        ├── 如果 leaseLost && phase == DOC_OCCUPIED
        │     → 回滚文档状态为 FAILED（锁丢了但文档被标记了 RUNNING）
        │
        ├── 如果 phase == FILE_SWITCHED
        │     → 删除旧文件（新文件已上线）
        │
        ├── 如果 stored != null && phase < CHUNK_COMPLETED
        │     → 删除新文件（分块未完成，向量数据不完整）
        │
        ├── 如果 stored != null（隐含 phase == CHUNK_COMPLETED）
        │     → 保留新文件 + WARN 日志（分块成功但元数据没切换，留人工处理）
        │
        └── lockManager.release(lease) —— 释放锁
```

### 3.3 五个执行阶段总表（必看）

> 这 5 个 Phase 是 **`ScheduleRefreshProcessor` 执行过程中的内存态阶段标记**，只用于 finally 中判断怎么补偿清理，**不会写入数据库**。

| Phase | 含义 | 到达该阶段前已经做了什么 | 典型失败处理 |
|------|------|----------------------|------------|
| `INIT` | 调度执行已启动，但还未占住文档运行权 | 已拿到 schedule 租约锁、已启动心跳、已加载 schedule/document、已计算 `nextRunTime`、已插入 exec 记录、已开始做远程变更检测 | 只写回 schedule/exec 结果；如果尚未占住文档，一般不需要回滚文档状态 |
| `DOC_OCCUPIED` | 已成功把 `Document.status` 改成 `RUNNING`，拿到文档业务运行权 | 在 `INIT` 基础上，已通过 `tryMarkRunning(docId)` 成功占住文档；此后当前流程对该文档拥有独占处理权 | 需要把文档从 `RUNNING` 收敛为 `FAILED`；若后续已上传新文件但未开始/完成分块，则 finally 会删除新文件 |
| `CHUNK_STARTED` | 已正式进入 `chunkDocument()`，开始分块/向量化 | 在 `DOC_OCCUPIED` 基础上，已上传新文件到对象存储，并准备调用 `chunkDocument()` | `Document.status -> FAILED`，`Schedule.lastStatus -> FAILED`，`Exec.status -> FAILED`；finally 删除新上传但未正式切换上线的新文件 |
| `CHUNK_COMPLETED` | 分块和向量化已经完成，但文档元数据还没切换到新文件 | `chunkDocument()` 已成功，重新查询文档状态确认是 `SUCCESS` | 保留新文件并打印告警，等待人工处理；不删除新文件，因为它可能已经对应一份有效结果 |
| `FILE_SWITCHED` | 文档元数据已切到新文件，新文件已经正式上线 | 已执行 `applyRefreshedFileMetadata()`，`Document.fileUrl/docName/fileType/fileSize` 等字段已指向新文件 | 这时通常是“收尾失败”而不是业务失败：例如 schedule 主状态写回失败、旧文件删除失败、释放锁失败；系统不回滚文档、不删除新文件，继续保留新结果并记录日志 |

### 3.4 三套状态体系（容易混淆，单独记）

| 维度 | 存储位置 | 典型值 | 表达的含义 |
|------|---------|-------|-----------|
| 文档业务状态 | `Document.status` | `pending / running / failed / success` | 这份文档当前业务上是否完成分块/向量化 |
| 调度最近一次结果 | `Schedule.lastStatus` | `success / failed / skipped` | 最近一次调度尝试的最终结果摘要 |
| 单次执行流水状态 | `Exec.status` | `running / success / failed / skipped` | 某一次具体执行从开始到结束的生命周期 |

### 4.1 第一组：先把系统怎么跑讲清楚

### Q1：当前知识库定时同步整体是怎么设计的？

**标准回答：**

这套设计可以先按 **三层模型** 来讲：

- `Document`：放文档本身的业务配置和处理状态，比如 `sourceType`、`sourceLocation`、`scheduleEnabled`、`scheduleCron`、`status`
- `Schedule`：放调度快照，比如 `cronExpr`、`nextRunTime`、`lockUntil`、`lastStatus`
- `Exec`：放每一次执行流水，记录这次调度到底跑成了 `running / success / failed / skipped`

整体流程是这样的：

1. 用户给 URL 文档配置 `cron` 后，系统会为这份文档维护一条 `Schedule`
2. 后台 `scan()` 每 10 秒扫描一次，到期且未加锁的任务会进入候选集合
3. 多个实例同时扫到没关系，只有抢到锁的实例才继续往下跑
4. 真正执行时，会先算出这次执行结束后要写回的 **下一次合法触发时间**
5. 然后插入一条 `Exec` 记录，表示本轮开始执行
6. 接着做远程文件变更检测，先看 `ETag / Last-Modified`，必要时再下载文件并算内容哈希
7. 如果确认文件变了，再去抢文档运行权，上传新文件、重新分块、重新向量化、切换元数据
8. 最后写回 `Schedule` 和 `Exec` 的结果，并在 `finally` 里按阶段做清理

**面试时一定要点到：**

- `nextRunTime` 的意思是 **下一次合法的 CRON 触发时间**，不是“当前时间再加 5 分钟”
- 这不是一个大事务，而是 **调度 + 锁 + 执行 + 补偿清理** 组合起来的流程
- `Q7 / Q8 / Q9` 最好和上面的 **五阶段表** 一起讲

---

### Q2：为什么要设计成“定时扫描 + 抢锁 + 异步执行”，而不是单机串行跑一个定时任务？

**标准回答：**

如果只是单机串行跑一个定时任务，短期看实现简单，但问题很快会出来：

- **单点故障**：机器挂了，所有同步都停了
- **吞吐受限**：多份文档同时到期时，只能排队，慢任务会堵住后面的任务
- **扩容困难**：任务量上来以后，只能硬顶单机能力

现在这套做法把职责拆开了：

- `scan()` 负责找候选任务
- 分布式锁负责决定“这一条到底谁来跑”
- 线程池负责异步执行，避免扫描线程被慢任务拖住

这样做的好处是，系统天然支持多节点部署，也更容易控制执行容量。面试时可以直接总结一句：

> **这不是普通定时任务，而是一套可以横向扩展的调度执行框架。**

---

### Q3：在多节点部署下，如何保证同一同步任务不会被多个实例重复执行？

**标准回答：**

这里靠的是 `Schedule` 这一层的 **租约锁**。多个实例都能扫到同一条到期任务，但往下执行前都会去做一次原子 `UPDATE`：

- 只有 `lockUntil` 为空或已经过期时，当前实例才能把 `lockOwner` 和新的 `lockUntil` 写进去
- 第一个更新成功的实例拿到执行权
- 其他实例更新 0 行，说明没抢到，直接放弃

所以，多实例下“看到同一条任务”是允许的，但“真正跑起来”只能有一个实例成功。

**别答偏：**

- 这里不是靠版本号字段做乐观锁
- 也不是靠 JVM 本地锁
- 核心是 **数据库单条条件更新的原子性**

---

### Q4：为什么这里选择数据库租约锁，而不是 Redis？

**标准回答：**

这题不要答成“因为某个数据库有 MVCC，所以它天然适合做分布式锁”。更准确的说法是：

1. **调度数据本来就在数据库里**
   把 `nextRunTime`、`lockUntil`、`lastStatus` 放在同一套存储里，调度状态和锁状态更容易保持一致
2. **当前规模下数据库条件更新完全够用**
   扫描周期是 10 秒级，批次默认 20 条，并不是高频高并发调度
3. **不需要为这条链路额外引入 Redis**
   少一个组件，部署和维护都简单

当前仓库默认运行在 **PostgreSQL** 上，但这里真正依赖的不是某个特定数据库的专有能力，而是**单条条件更新的原子性**。

所以这是一笔很典型的工程账：**当前规模下，用数据库本身承载调度状态和租约锁，简单、够用、也更容易保证一致性。**

如果未来任务量上到万级、调度粒度压到秒级甚至毫秒级，再考虑 Redis + Lua 那一套也不晚。

---

### Q5：为什么锁要做成“租约锁 + 心跳续约”，而不是拿到锁后一直持有到任务结束？

**标准回答：**

因为“拿到锁后一直持有”有一个很致命的问题：**执行者一旦宕机，锁就可能永远不释放。**

所以这里设计成租约锁：

- 抢锁成功时，只拿到一段时间内的执行权
- 任务还活着，就持续续约
- 实例一旦崩溃，心跳停掉，锁自然过期
- 锁过期以后，其他实例就能接手

这就是为什么它比“永久锁”更适合分布式任务。它不是为了让逻辑更复杂，而是为了让系统有 **故障自愈能力**。

**补一句更完整：**

- `lockUntil` 解决的是“锁什么时候自然失效”
- 心跳续约解决的是“长任务别被误判成死任务”

---

### Q6：为什么除了调度锁之外，还要再做一层 `Document.status = RUNNING` 的业务状态保护？

**标准回答：**

因为 **调度锁** 和 **文档运行状态** 保护的根本不是同一类资源。

- `Schedule` 锁保护的是：**同一条调度记录，不要被多个实例重复执行**
- `Document.status` 保护的是：**同一份文档，不要被多个入口同时处理**

这里最容易被追问的点是：手动分块和定时同步都可能处理同一份文档。  
如果只有调度锁，没有文档状态保护，就可能出现：

- 定时同步在处理这份文档
- 用户又手动点了一次分块
- 两边都去上传文件、分块、切元数据
- 最后业务结果互相覆盖

所以这两层不是重复，而是不同维度的互斥：

> **调度锁管 schedule，文档状态管 document。**

---

### Q7：如果任务执行到一半失败，系统是怎么处理失败和状态流转的？

> **这题一定结合上面的 `3.3 五个执行阶段总表` 来讲。**

**标准回答：**

这套系统不是失败了就“统一回滚”，而是先判断失败时已经走到哪个阶段，再决定怎么收敛状态。

可以按下面这张表讲：

| 出错位置 | `Document.status` | `Schedule.lastStatus` | `Exec.status` | 文件处理 |
|------|-------------------|----------------------|---------------|----------|
| 还没占住文档运行权 | 一般不动 | `failed` 或 `skipped` | 写本次执行结果 | 通常没有新文件需要清理 |
| 已占住文档，但分块还没完成 | 改成 `failed` | 改成 `failed` | 改成 `failed` | 删除新上传但还没正式生效的文件 |
| 分块已完成，但元数据还没切换 | 文档结果已接近成功 | 一般记失败并告警 | 记失败 | **保留新文件**，留人工处理 |
| 元数据已经切到新文件 | 不回滚文档 | 主状态尽量写回 | `exec` 至少保留结果 | 删除旧文件走 best effort |

这里真正重要的不是死记哪一行表，而是讲清楚一个原则：

> **失败处理要和当前阶段已经产生的副作用对应。**

另外还要补一句：如果执行进程崩了，导致文档长时间卡在 `running`，后面还有看门狗把它收敛成 `failed`，避免文档永远锁死。

---

### Q8：为什么 `finally` 里的清理逻辑不能统一做，而必须按阶段处理？

**标准回答：**

因为这条链路跨了数据库、对象存储、分块/向量化结果，不存在一个可以把所有动作都一把回滚掉的“大事务”。  
如果失败后统一做同一套清理，风险很大：

- 统一删新文件，可能删掉已经对应有效结果的新文件
- 统一删旧文件，可能把线上还在用的旧文件删掉
- 统一回滚文档状态，可能把已经成功切换的数据又打回去

所以 `phase` 的意义不是单纯记录流程走到哪里，而是 **驱动恢复策略**。

面试时可以直接说：

> **阶段不是为了看日志好看，而是为了失败时知道该删什么、保什么、回滚什么。**

### 4.2 第二组：面试官最爱追问的设计取舍

### Q9：你觉得这套定时同步设计里最大的风险点是什么？如果出现部分成功、部分失败，你怎么处理？

**标准回答：**

这套设计最大的风险点，不是“会不会准点到秒执行”，而是 **跨资源的一致性问题**。

一次同步会同时碰到：

- `Document / Schedule / Exec` 这些数据库状态
- 对象存储里的新旧文件
- 分块和向量化结果

这些东西不在同一个本地事务里，所以最容易出现“前面成功了，后面失败了”的情况。  
比如：

- 新文件上传成功了
- 分块和向量化也跑完了
- 但元数据切换失败了

这时系统不可能靠一个数据库事务把所有状态全部回滚回去，只能做 **补偿式恢复**：

- 能自动清理的就清理
- 不能安全回滚的就保留并告警
- 让系统最终收敛到一个可理解、可继续处理的状态

这题面试时千万别答成“最大的风险是 cron 不准”。那个只是调度精度取舍，不是这套架构真正的风险点。

---

### Q10：为什么锁状态和业务状态要分开处理？为什么看门狗恢复的是业务状态，而不是锁本身？

**标准回答：**

因为这两套状态的职责完全不同：

- **锁状态** 解决的是：谁现在有执行权
- **业务状态** 解决的是：文档现在处于什么处理状态

锁本身有 TTL，会自然过期：

- 续约停了，锁就到期
- 到期以后，别的实例就能重新抢

所以锁通常不需要看门狗强制恢复。  
真正危险的是业务状态残留：

- 文档已经被标成 `running`
- 但执行进程已经崩了
- 锁可能早就过期了
- 文档状态却还卡在 `running`

所以看门狗恢复的是 **业务脏状态**，不是锁本身。

这题一句话版本就是：

> **锁是协调层状态，业务状态是资源层状态，两者生命周期不同，恢复手段也不同。**

---

### Q11：为什么任务开始时已经抢到锁了，结果写回时还要再次确认当前执行权？

**标准回答：**

因为“开始时抢到锁”只能说明：**任务启动那一刻，锁是我的。**

但任务执行过程中可能发生这些事：

- 心跳续约失败
- 数据库短暂抖动
- 线程卡顿太久
- 锁已经过期，被别的实例接手

如果这个时候当前实例还不做二次确认，直接把 `Schedule.lastStatus` 写回去，就可能把新执行者已经写好的结果覆盖掉。

所以写回主表时一定要再带一次 `lock_owner = token` 条件，本质上是在做：

> **执行前拿授权，提交前再验一次授权。**

这题的核心是防止 **旧执行者晚到，把新执行者结果覆盖掉**。

### Q12：为什么远程文件变更检测要做成“两段式”，而不是每次都直接拉全量重建？

**标准回答：**

如果每次调度都直接下载远程文件、算哈希、重新分块和向量化，成本太高。  
但如果只看 `ETag`，又不够稳，因为不同源站返回 `ETag` 的方式不完全一样。

所以这里做成两段式：

1. 先用 `HEAD` 请求拿 `ETag / Last-Modified` 做轻量预检
2. 只有预检不能确定“没变”时，才真正下载文件并算内容哈希

这个设计的价值在于：

- **大多数没变的文件**，可以很快跳过
- **少数需要确认的文件**，再用内容哈希做最终兜底

一句话总结：

> **先用便宜的方法过滤大多数，再用昂贵但准确的方法做最终确认。**

### Q13：如果系统里既有手动同步入口，又有定时同步入口，你怎么保证它们不会并发处理同一份文档？

**标准回答：**

这里其实是两层保护：

1. **定时任务之间**
   靠 `Schedule` 锁，保证同一条 schedule 同一时刻只被一个实例执行
2. **手动入口和定时入口之间**
   靠 `Document.status = RUNNING` 这一层业务互斥

面试官常追问：“如果两个入口几乎同时进来，会不会都成功？”  
答案是：**最终不会。**

因为最后的仲裁点不是前面的 if 判断，而是数据库里的条件更新：

- 手动入口会尝试把文档状态改成 `RUNNING`
- 定时入口也会通过 `tryMarkRunning(docId)` 抢这个状态
- 只有一个更新能成功

所以这题的标准收束方式是：

> **定时和定时的冲突靠 schedule 锁，手动和定时的冲突靠 document running 状态。**

### Q14：如果调度系统瞬时堆积、执行容量不足，你怎么做背压，而不是把整个系统打爆？

**标准回答：**

这题不是在考消息队列，而是在考你有没有 **控制任务入场速度** 的意识。

当前实现里，已经有三层天然背压：

1. **扫描节奏受控**
   `scan()` 不是无限拉取，而是固定周期扫描
2. **每次扫描批量受控**
   不是所有到期任务一次性全放进来，而是按 `batchSize` 限制
3. **执行容量受控**
   调度任务提交到 `knowledgeChunkExecutor`，该线程池是有界队列 + `AbortPolicy`；吃不下时会抛 `RejectedExecutionException`，扫描线程捕获后释放租约，让下一轮再捞

所以它的表现不是“系统被打爆”，而是：

- 执行延迟会上升
- 吞吐会下降
- 但不会无限堆积到把 JVM 和下游一起拖死

如果后面规模再涨，还可以继续往下加：

- 动态 batch
- 按知识库限流
- 按源站限流
- 任务积压监控和告警

### Q15：为什么失败任务不是立即高频重试，而是继续按调度节奏往后推进？

**标准回答：**

因为这类失败很多不是“马上重试就能好”的那种失败。常见原因更可能是：

- 远程源站不可用
- 文件异常
- 对象存储异常
- 分块或向量化链路异常

如果失败后立刻高频重试，会反复下载、反复上传、反复分块，最后把资源消耗放大。  
而当前这套系统本质上是 **cron 周期调度系统**，不是失败重试框架。

所以它的思路是：

- 把这次失败记录下来
- `nextRunTime` 继续推进到下一个合法 cron 时刻
- 等下一轮正常调度再跑
- 如果业务上很急，再让人工手动触发

**这题一定要答准：**

> **当前这条链路没有专门的高频重试框架，失败后主要还是按下一次 cron 节奏继续推进。**

### Q16：你的租约续约机制在当前规模下为什么成立？它的容量边界在哪里？

**标准回答：**

这套续约机制在当前规模下成立，靠的是三个前提：

1. **TTL 够宽松**
   默认锁时长是 900 秒，心跳并不是贴着过期时间续
2. **续约动作够轻**
   本质上就是一条带 `scheduleId + token` 条件的单行 `UPDATE`
3. **活跃任务数量被前面的扫描批次和线程池限制住了**
   不会一下子冒出几千个长任务同时续约

但它不是无限扩展的。容量边界大致会出现在这些场景：

- 同时活跃的长任务数量明显升高
- cron 频率越来越密
- 数据库续约延迟开始变大
- 单线程心跳器排队太久

到那时，更合理的演进方向会是：

- 多线程 `ScheduledExecutorService`
- 心跳分片
- 更细的调度分区
- 甚至把协调能力迁到更适合高并发锁的组件

这题最成熟的回答不是说“现在方案最好”，而是：

> **我知道它为什么现在够用，也知道它什么时候该升级。**

## 五、最后只记这 8 句

> 如果临近面试时间不够，先把下面这 8 句背熟。

1. **这套系统分三层：`Document` 管业务配置和文档状态，`Schedule` 管调度快照和租约锁，`Exec` 管单次执行历史。**
2. **整体架构是“定时扫描 + 抢锁 + 异步执行 + 阶段化补偿”，不是单机串行定时任务。**
3. **`Schedule` 锁解决的是同一条调度记录不要重复执行，`Document.status = RUNNING` 解决的是同一份文档不要被多个入口同时处理。**
4. **锁做成租约锁加心跳续约，是为了让执行者宕机后任务还能被其他实例接管。**
5. **系统真正的风险点不是 cron 精度，而是数据库、对象存储、向量结果之间的部分成功问题。**
6. **失败后不是统一回滚，而是按阶段补偿：该删新文件就删，该保留就保留，该告警就告警。**
7. **写回主表时要再次校验 `lock_owner = token`，目的是防止旧执行者覆盖新执行者。**
8. **当前链路没有高频失败重试框架，失败后主要还是推进到下一次 `nextRunTime`，按 cron 节奏继续跑。**
